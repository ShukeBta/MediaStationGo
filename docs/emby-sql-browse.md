# Emby 浏览 SQL 改造

## 范围与状态

本地实现；尚未推送、部署或完成 PostgreSQL/Filmly 真实请求验收。

本轮覆盖剧集 `/Items`、剧集 `/Items/Latest`、剧集媒体库封面候选、`/Genres`。
不改网页接口、播放地址、继续观看的播放进度逻辑，不宣称所有 Emby 接口都已优化。

## 查询与数据来源

- 保留 Emby 原有公共 ID 计算规则，不用网页 `series_key` 替换，不向 `Media.SeriesID` 填入虚拟 ID。
- `media` 上的 Emby 字段是现有身份、标题、日期和分类函数的派生投影，不是独立业务数据源；没有新增响应缓存或整表汇总表。
- 剧集列表先在数据库按分组键聚合，按索引定位代表行，SQL 排序分页后，只加载选中组的完整媒体记录。选中组仍沿用原有详情构造逻辑；完整记录读取量与当前页包含的集数有关，不是只读取每部剧一条记录。
- 搜索、可见性、类型筛选和收藏条件在分页前执行；没有大库转旧 Go 分组的运行时分支，也不再用 50,000 集截断列表分组。
- 封面只返回少量经 SQL 选择、去重的候选，保留不同图片类型优先级及 Series 背景所有权。
- Genres 使用原分类函数预计算的类型变体，在 SQL 中计数、筛选和分页；库类型变化立即选择相应变体。分类配置指纹变更会使旧投影失效。
- 保留普通列表与 Latest 原有的分段作品分组差异，不擅自合并协议身份。

## 客户端排序约定

- 保留 `SortBy` 的字段优先级，分别读取对应 `SortOrder`；单一方向应用于未单独指定方向的字段。
- `DateCreated`、`DateLastContentAdded` 使用组内最新入库时间。
- `PremiereDate` 只使用有效首播日期，不借用年份或入库时间。
- `ProductionYear`、`CommunityRating` 分别使用相应字段。
- 缺少对应字段的作品置后，按名称升序、ID 升序排列；不进行“时间与名称混合成对比较”，避免非传递排序导致翻页不稳定。
- 时间相同则继续客户端后续条件；未指定名称次序时附加名称升序，最后用 ID 升序消除并列。未指定有效排序字段时按名称。

## 写入与升级边界

- Upsert、已接入的事务更新/迁移入口、本地扫描实际批量插入切片同步准备投影。
- 修复本地扫描原先对临时副本准备分组字段、却插入另一份数据的问题。
- 原始分组/分类输入被直接 SQL 修改时，数据库触发器标记投影失效；软删、硬删通过原媒体表可见性直接生效，不维护另一份删除状态。
- 初始化在 HTTP 开放前完成；按批次锁定源记录并计算，PostgreSQL 每批通过一次 JSON recordset UPDATE 写入。初始化失败明确停止启动。
- 后续维护只修复失效记录，不周期性重算全库。请求最多修复 500 条当前范围内的失效记录；超出则明确报错，不静默返回缺项或转旧算法。
- 迁移遵循原 ID 规则：没有显式 SeriesID 的虚拟 ID 本来就包含库身份，因此换库会重新计算；不承诺虚拟 ID 跨库恒定。媒体自身 ID 不由本改造更换。
- 选页后发生删除或迁移导致组成员不一致时明确失败，不返回残缺组。普通多次分页并不提供跨请求的数据库快照。
- 初始化/回填不访问云盘、不触发扫描、刮削或真实 115 请求。

## 本地验证记录（2026-09-07）

Windows / i5-12600KF / SQLite 内存库，使用正式数据库迁移创建索引。
合成数据每部 55 集，包含简介、搜索别名和播放字段。数据创建及初始化不计入请求基准；每项 3 次。

同一份 9,735 集样本，12 项列表服务层对比：

| 实现 | 单次时间 | 单次分配量 |
| --- | ---: | ---: |
| 测试专用旧全量读取参考 | 1,107 ms | 412.2 MB |
| 新 SQL 分页 | 104 ms | 33.8 MB |

规模测试（独立一次运行，数值允许有正常波动）：

| 集数 / 部数 | 12 项/页 | 48 项/页 |
| --- | ---: | ---: |
| 9,735 / 177 | 94 ms | 257 ms |
| 97,350 / 1,770 | 594 ms | 763 ms |

12 项单次分配量约 33.9→34.3 MB；48 项约 137.0→137.4 MB。
数据库仍需聚合当前筛选范围，这不是 O(1) 查询，也不说明十倍规模没有任何性能成本。

覆盖排序优先级、缺失日期、同名跨页、返回字段、类型筛选、分类配置和库类型变化、分段作品、封面去重、新入库、迁移、直接更新失效、初始化幂等、并发成员变化。

本地没有可用 PostgreSQL/Docker 可执行环境，上述不是 PostgreSQL 执行计划、外部 HTTPS 耗时或 Filmly 设备实测。
正式发布前仍需对精确 SHA 构建不可变镜像，完成隔离 PostgreSQL 初始化/索引/执行计划验证，再使用真实客户端请求参数复测；不能直接以本地基准宣布线上已生效。
