# 剧集详情请求阻塞修复

## 范围

针对 Episodes 版本折叠重复查库，以及图片缓存维护阻塞缩略图响应。
不修改分组、排序、媒体迁移、入库写入或图片选择规则；不调整客户端并发、
数据库连接池上限、缓存容量与清理周期。

## Episodes

在 episodeItems 的筛选和版本折叠之前加载已有的请求内库快照，后续响应组装
复用同一上下文。没有跨请求缓存或失效窗口；下一次请求重新读取媒体库事实。
读取失败直接返回错误。

回归样本为 48 集：修复前访问 libraries 97 次，修复后 1 次。
比较提前传入快照与正常调用的完整 JSON，内容一致。该数值只表示库表查询次数，
不是所有 SQL 总数，也不是生产耗时收益。

## 图片

后台缩略图清理持有 variantCacheMu 遍历目录；原图清理持有 mu 遍历目录。
之前，缩略图生成完成后还必须等待这些锁才能写缓存、返回图片。

现在缓存写入采用非阻塞准入：维护或其他写入占锁时，不缓存本次缩略图，
直接返回已经生成的完整图片。后续请求可以重新生成并缓存。清理调度入口也不等待
维护锁，避免刚写完缓存后在调度处重新被阻塞。

这是一项明确的资源策略：短暂争用时可能多做一次缩放，换取响应不等待整库清理。
没有新增后台写入队列、不返回占位图、不忽略图片生成错误、不放宽磁盘容量限制。
保留原来的锁内容量检查与字节记账，避免清理和写入并行导致容量统计失真。

回归测试分别占住两种维护锁，在释放锁之前断言完整图片响应已完成；检查尺寸、
HTTP 状态、后续可缓存，并比较两次响应字节一致。旧实现不能通过该测试。

## 实机证据边界

2026-09-09 09:56 的 Filmly/163 日志：三张图片首字节约 4.07 秒，已有原图缓存，
三张新缩略图同时落盘。该现象与维护锁阻塞吻合，但历史现场没有锁采样。
本次本地测试证明并消除这一可复现阻塞机制，不代表已经证明实机全部 4 秒延迟来源。
仍需发布后的同设备验证；当前变更本身不是生产发布。
